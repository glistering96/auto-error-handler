01 · Overview

한눈에 보는 시스템

서비스가 HTTP로 오류와 재현 정보를 보내면 API가 Incident와 분석 Job을 저장합니다. Codex는 먼저 읽기 전용으로 분석하고, 승인 이후에만 별도 worktree에서 패치합니다.

외부 서비스오류·stack trace·재현 정보
→
API + PostgreSQLIncident·상태·Job Queue
→
Codex Runner분석 → 승인 → 패치·검증
핵심 규칙: writable worktree와 Patch Job은 승인 transaction 이후에만 생성됩니다.

06 · MQ Structure

MQ 구조: PostgreSQL Job Queue

MVP에는 별도 broker가 없습니다. jobs 테이블이 command queue 역할을 하며 FOR UPDATE SKIP LOCKED로 중복 claim을 막습니다.

Control APIANALYZE/PATCH insert
→
PostgreSQL jobsPENDING → RUNNING
→
Job Workerclaim → Runner
Worker claim SQL
WITH candidate AS (
  SELECT id FROM jobs
  WHERE status='PENDING' AND available_at <= now()
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE jobs
SET status='RUNNING', locked_by=:worker_id,
    locked_at=now(), attempt=attempt+1
WHERE id IN (SELECT id FROM candidate)
RETURNING *;
Atomicity

상태+Job

Incident와 Job이 같은 transaction이므로 MVP에는 Outbox가 필요 없습니다.

Dedup

결정적 key

ANALYZE:<incident>, PATCH:<approval> unique key를 씁니다.

Recovery

stale 복구

오래된 RUNNING을 PENDING으로 돌리고 최대 2회 시도합니다.

PENDING→RUNNING→SUCCEEDED 또는 FAILED
MVP · 지금

PostgreSQL Queue

단순하고 도메인 상태와 Job을 원자적으로 저장합니다.

운영 · 나중

RabbitMQ

높은 처리량, backpressure, retry/DLQ가 실제 필요할 때 도입합니다.

전환 경계: PostgresJobQueue를 RabbitJobQueue로 교체하고 DB Outbox를 추가합니다. HTTP API, Incident 상태 머신, Codex 계약은 유지됩니다.

09 · MVP Decisions

구현 전에 확정할 의사결정

아래 항목은 구현 중 자연스럽게 결정되도록 두면 API·DB·Worker가 서로 다른 가정을 갖기 쉽습니다. 권장 기본값으로 먼저 고정하고 E2E 결과로 바꿉니다.

의사결정MVP 권장값영향
Incident groupingproducer fingerprint 우선, 없으면 exception type + top frame + route 정규화과도한 합침·분할과 분석 비용
기준 commitrelease.commitSha 필수 권장, 없으면 등록된 default branch HEAD snapshot재현성, 오래된 분석 승인 처리
승인 유효성분석 SHA와 현재 SHA가 다르면 409 후 재분석잘못된 코드에 patch 방지
재시도infra 실패만 지수 backoff 2회, 코드·검증 실패는 자동 재시도 안 함중복 비용과 무한 loop
timeout·크기분석 10분, 패치 15분, validation 10분; payload 256KB·diff 2,000줄용량 계획과 DoS 경계
validation command서비스 등록 시 allowlist; event의 문자열은 실행 금지RCE 방지와 신뢰도
patch 범위허용 경로, 최대 파일 수, binary·symlink·submodule 금지쓰기 sandbox 안전성
실패 결과 보존구조화 error code, 제한된 log, worktree는 조사 TTL 후 삭제디버깅과 디스크 사용량
승인 UI/API현재는 API 직접 승인, 인증·승인자 identity는 후속MVP 노출 범위를 개발망으로 제한
성공의 정의diff 정책 통과 + 등록 validation 전체 성공일 때만 PATCH_READY상태 머신과 E2E acceptance
먼저 결정할 4개: fingerprint 규칙, 기준 SHA, validation allowlist, patch 제한. 나머지는 권장값으로 시작해도 구조 변경이 작습니다.
10 · Scale-out

수평 확장에 필요한 것

API는 먼저 stateless로 늘릴 수 있지만 Worker는 저장소·worktree·Codex 프로세스를 소비합니다. 따라서 API replica 수보다 Job 동시성, 격리, recovery를 먼저 계측해야 합니다.

1 · Stateless API

공유 상태 제거

모든 workflow 상태를 PostgreSQL에 두고 cursor pagination, connection pool, readiness를 적용합니다.

2 · Worker Lease

안전한 다중 claim

SKIP LOCKED, locked_by/locked_at, heartbeat, stale lease 회수, idempotent finalize가 필요합니다.

3 · Execution Isolation

Job별 workspace

고유 경로, CPU·메모리·시간 제한, cleanup, host당 concurrency 제한으로 noisy neighbor를 막습니다.

4 · Repository Cache

공유 clone 금지

read-only mirror cache와 Job별 worktree를 분리하고 동일 repo lock과 디스크 quota를 둡니다.

5 · Observability

병목을 숫자로 확인

queue depth/age, claim latency, 실행 시간, 실패율, retry, token 비용, 디스크 사용량을 측정합니다.

6 · Capacity Guard

Backpressure

서비스별 동시성·rate limit, global quota, max pending, admission control로 폭주를 제한합니다.

전환 신호추가 구성
PostgreSQL polling/쓰기 부하가 병목Transactional Outbox + RabbitMQ publisher + durable queue
retry 분리와 장기 backlog 필요retry queue, DLQ, poison-message 격리, replay 도구
여러 호스트에서 patch 실행container/VM sandbox, artifact/object storage, 중앙 log
서비스·조직별 보안 경계 필요인증, tenant key, RBAC, secret manager, audit log
운영 배포 자동화GitHub App, branch/PR lifecycle, webhook reconciliation
권장 전환 순서: API replica → PostgreSQL HA/pool → Worker replica와 lease → 실행 sandbox/관측 → 실제 병목이 확인될 때 Outbox + RabbitMQ. RabbitMQ만 먼저 넣어도 Codex 실행 처리량은 늘지 않습니다.
