# ADR-0001: 오류 사건의 지문과 기준 커밋 고정

- Status: Accepted
- Date: 2026-09-24
- Decision owner: Auto Error Handler MVP
- Related decision: DEC-004, DEC-005, DEC-006, DEC-024, DEC-025
- Supersedes: 없음

## 배경

기존 계약은 `fingerprint`가 없을 때 스택 추적에서 애플리케이션 프레임을 추정하도록 제안했지만, 언어와 배포 경로에 따라 같은 규칙을 적용하기 어렵다. 또한 작업자가 분석을 시작할 때 기본 브랜치의 최신 커밋을 읽으면, 오류 접수 이후 브랜치가 이동한 경우 분석 대상이 바뀐다. 같은 지문이라도 서로 다른 배포 커밋의 오류를 하나로 합치면 사건 하나의 기준 SHA로 모든 발생 기록을 설명할 수 없다.

## 검토한 선택지

- 지문을 선택적으로 받고 스택 추적에서 추정한다: Producer의 부담은 작지만 서로 다른 원인을 합칠 수 있다.
- 지문을 필수로 받고 커밋 SHA별로 사건을 나눈다: Producer가 안정적인 지문을 만들어야 하지만 사건과 분석 대상 코드의 관계가 명확하다.
- 기준 SHA를 작업자가 결정한다: 접수는 빠르지만 대기 중 브랜치 이동에 영향을 받는다.

## 결정

1. 모든 내부 리소스 ID는 UUIDv4로 생성한다. 외부 `eventId`와 승인용 `Idempotency-Key`는 유효한 UUID이면 받는다.
2. `fingerprint`는 MVP 요청의 필수 필드다. 앞뒤 공백을 제거하고 유니코드 NFC로 정규화하되 대소문자는 보존한다. 정규화한 결과가 비어 있으면 `422`를 반환한다. 스택 추적을 이용한 자동 지문 생성은 MVP에 넣지 않는다.
3. 사건 묶기 키는 `(service_id, fingerprint, base_commit_sha)`다. 처리 중인 같은 키의 사건에만 발생 기록을 추가한다. 동일 지문이더라도 전체 커밋 SHA가 다르면 별도의 사건으로 만든다.
4. 접수 API는 새 이벤트의 DB 쓰기 전에 `release.commitSha`를 저장소의 전체 커밋 객체 ID로 검증·확정한다. 값이 없을 때만 그 요청을 처리하며 읽은 기본 브랜치 `HEAD`를 사용한다. Git 조회는 DB 트랜잭션 밖에서 수행한다. 제공된 SHA가 없거나 커밋을 가리키지 않으면 `422`, 저장소를 일시적으로 읽을 수 없으면 `503`을 반환하고 아무 이벤트도 저장하지 않는다. 두 경우 모두 다른 SHA로 조용히 대체하지 않는다.
5. 동일 `(service_id, event_id)`의 재요청은 먼저 기존 체크섬과 비교한다. 같은 요청이면 Git을 다시 조회하지 않고 기존 사건 ID와 현재 상태를 `duplicate=true`로 반환한다. 다른 요청이면 `409`를 반환한다. 새 `eventId`에 대해서만 SHA를 새로 확정한다.
   체크섬은 [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785.html)에 따라 정규화한 요청 JSON의 UTF-8 바이트에 SHA-256을 적용한다. 객체 키 순서와 공백만 다르면 같은 요청이다. 중복 객체 키는 `400`, 정규화할 수 없는 수치는 `422`로 거부한다. 체크섬은 민감 정보 제거 전에 계산하고 원본 요청은 영구 저장하지 않는다.
6. 최초 접수와 사건 생성 트랜잭션은 SHA를 검증한 정규화된 저장소 경로와 확정한 SHA를 `incidents.repository_path_snapshot`·`base_commit_sha`에 저장하고 이벤트·발생 기록·`ANALYZE` 작업을 함께 저장한다. 작업자는 이 저장소와 SHA를 다시 선택하지 않고 존재 여부만 재확인한다.
   `services.repository_path` 변경은 해당 서비스에 처리 중인 사건이 있으면 거부한다. 따라서 같은 사건 묶기 키 아래에 서로 다른 저장소 경로가 섞이지 않는다.
7. MVP 분석은 사건의 첫 이벤트 하나를 입력으로 고정한다. 사건 생성 시 `incidents.first_error_event_id`를 저장하고 첫 분석 선점 때 `analysis_runs.input_error_event_id`에 복사한다. 재시도해도 이 값을 유지한다. 이후 같은 사건에 추가된 오류는 `occurrence_count`만 증가시키고 현재 분석을 다시 시작하지 않는다. `incidents.version`은 상태 전이에만 사용한다.

## 영향

- 외부 Producer가 `fingerprint`를 보내야 한다. 누락 요청은 기존의 선택 필드 계약과 호환되지 않으므로 JSON Schema와 예시를 함께 바꾼다.
- DB의 처리 중 사건 고유 인덱스에 `base_commit_sha`를 포함한다. 접수 과정에서 저장소 조회가 추가되지만, 분석 대상 커밋이 접수 후 바뀌지 않는다.
- 새 발생 기록의 재현 정보가 기존 분석에 자동으로 들어가지는 않는다. 재분석은 MVP 이후에 설계한다.

## 검증

- `fingerprint` 누락·공백 요청이 `422`인지 확인한다.
- 기본 브랜치가 접수 후 이동해도 분석·승인·패치의 SHA가 최초 접수 때 저장한 SHA와 같은지 확인한다.
- 처리 중인 사건이 있는 서비스의 저장소 경로 변경은 거부하고, 정책 변경만 허용하는지 확인한다.
- 서로 다른 SHA의 동일 지문은 별도 사건, 같은 SHA의 동일 지문은 하나의 처리 중 사건인지 동시 접수 시험으로 확인한다.
- 중복 `eventId`의 재전송은 브랜치 이동이나 저장소 장애 중에도 기존 사건 ID와 현재 상태를 반환하며 새 Git 조회를 하지 않는지 확인한다.
- 같은 의미의 JSON에서 객체 키 순서·공백만 바꾼 재요청은 같은 체크섬을 얻고, 배열 순서·문자열 값 변경은 충돌하는지 확인한다. 중복 객체 키와 정규화 불가 수치도 거부한다.
- 분석 중 발생 기록이 늘어도 `version`은 바뀌지 않고, 고정된 첫 이벤트를 사용한 분석 완료가 성공하는지 확인한다.
