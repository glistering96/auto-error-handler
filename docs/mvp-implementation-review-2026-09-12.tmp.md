# Auto Error Handler MVP 요구사항 검토

상태: 과거 검토 기록 — 현재 구현 결정은 의사결정 대장 참조
검토일: 2026-09-12
검토 대상: MVP 범위, 의사결정 대장, OpenAPI와 JSON Schema, DB·작업자·Codex 계약, 실행 계획
검토 기준: 실제 서비스에 꼭 필요한 기능과 최소한의 안전장치가 빠짐없이 정의되어 있는가

> 이 문서는 2026-09-12 당시의 검토 결과입니다. 이후 확정된 값과 구현 순서는 [의사결정 대장](decision-register.md)과 [MVP 실행 계획](mvp-execution-plan.md)을 따릅니다.

## 1. 한눈에 보는 결론

MVP의 큰 방향과 핵심 요구사항은 잘 잡혀 있습니다.

이 서비스가 제공하려는 가치는 다음 흐름에 분명하게 드러납니다.

```text
오류 접수
  → 같은 원인의 오류를 하나의 인시던트로 묶음
  → PostgreSQL 작업 대기열에 분석 작업 등록
  → 저장소를 바꾸지 않는 읽기 전용 분석
  → 사용자가 분석 결과 확인
  → 특정 분석 결과와 기준 커밋 승인
  → 별도 작업 공간에서 패치 생성
  → 실제 Git 변경 내용과 테스트 결과 검증
  → 검증된 변경 내용 제공
```

HTTP로 오류를 받고 PostgreSQL로 작업을 관리하며, 최종 결과는 검증된 변경 내용까지만 제공하도록 범위를 잘 줄였습니다. 메시지 큐, Pull Request 생성, 자동 배포, 화면과 알림을 뒤로 미룬 판단도 적절합니다.

승인 요청은 본문 없이 처리하기로 확정했습니다. 서버가 승인 시점에 유일한 성공 분석과 기준 커밋을 직접 조회하여 승인 기록에 고정합니다.

구현을 시작하기 전에 남은 핵심 보완 사항은 아래 두 가지입니다.

1. 분석 이후 서비스 정책이 바뀌었을 때 어떤 정책을 적용할지 정해야 합니다.
2. Codex와 검증 명령의 외부 네트워크 접근을 막는 기준이 필요합니다.

이 두 가지를 보완하면 요구사항 문서는 구현을 시작하기에 충분합니다. 나머지는 구현하면서 계약 테스트로 구체화해도 됩니다.

### 영역별 평가

| 영역 | 평가 | 검토 의견 |
|---|---|---|
| 제품 목표와 사용자 가치 | 잘 정리됨 | 분석은 자동화하고 저장소 변경은 승인 뒤에만 허용 |
| MVP 범위 | 적절함 | 첫 검증에 필요하지 않은 기능을 뒤로 미룸 |
| 오류 입력과 중복 처리 | 잘 정리됨 | 스키마, 크기 제한, 중복 키와 충돌 처리 기준이 있음 |
| 인시던트와 상태 흐름 | 일부 보완 필요 | 새 오류 발생 시점과 상태 버전의 관계가 불분명 |
| 승인 안전장치 | 대체로 잘 정리됨 | 승인 방식은 확정됐으며 승인 당시 정책 고정만 필요 |
| 작업 대기열과 장애 복구 | 잘 정리됨 | 실행별 토큰, 임대 갱신, 재시도 횟수와 24시간 제한이 확정됨 |
| Git과 명령 실행 안전 | 잘 정리됨 | 경로, 변경량, 파일 형식, 실행 명령을 제한 |
| Codex 실행 격리 | 일부 보완 필요 | 파일 접근은 구분했지만 외부 통신 기준이 없음 |
| 조회 API | 충분함 | 페이지 나누기는 첫 MVP에서 단순화 가능 |
| 시험과 완료 기준 | 잘 정리됨 | 중복, 장애, 오래된 결과, 정책 위반을 시험하도록 정의 |
| 기준 문서의 우선순위 | 잘 정리됨 | 결정 사항부터 API, 스키마, 이관, 테스트 순으로 명확함 |

## 2. 특히 잘 잡힌 요구사항

### 2.1 서비스가 책임질 범위가 분명합니다

- 개별 오류를 전달하는 데서 끝나지 않고, 같은 원인의 오류를 하나의 인시던트로 관리합니다.
- 분석, 승인, 패치 생성과 검증 상태를 서비스가 직접 관리합니다.
- 자동 병합이나 배포까지 가지 않고, 검증된 Git 변경 내용을 결과로 제공합니다.

이 정도면 첫 MVP가 무엇을 증명해야 하는지 충분히 분명합니다.

### 2.2 승인 전에는 저장소를 바꿀 수 없도록 했습니다

- 분석과 패치는 서로 다른 Codex 대화와 Git 작업 공간에서 실행합니다.
- 승인 전에는 패치 작업과 쓰기 가능한 작업 공간을 만들지 않습니다.
- 승인 기록, 패치 실행 기록, 패치 작업, 인시던트 상태를 한 트랜잭션으로 저장합니다.
- 사용자가 승인한 커밋과 실제 패치 작업 공간의 커밋이 같아야 합니다.

이 경계는 기능 범위를 더 줄이더라도 반드시 유지해야 합니다.

### 2.3 Codex의 답을 그대로 믿지 않고 실제 결과를 다시 확인합니다

- Codex 응답이 정해진 형식을 따르는지 검사합니다.
- 실제 Git 변경 내용을 다시 읽습니다.
- 허용 경로와 금지 경로를 검사합니다.
- 바뀐 파일 수와 변경 줄 수를 제한합니다.
- 바이너리 파일, 심볼릭 링크, 하위 모듈 변경을 막습니다.
- 서비스 설정에 등록된 명령만 `shell=False`로 실행합니다.
- 모든 검증을 통과해야만 `PATCH_READY`로 처리합니다.

인공지능의 설명과 실제 저장소 상태를 분리해 확인한다는 점이 좋습니다.

### 2.4 중복 요청과 장애를 예외가 아닌 정상 상황으로 다룹니다

- `(service_id, event_id)`를 고유하게 만들고 요청 내용의 체크섬을 비교합니다.
- 오류, 인시던트, 발생 기록, 분석 작업을 한 트랜잭션으로 저장합니다.
- PostgreSQL의 `SKIP LOCKED`를 사용해 작업을 하나씩 가져갑니다.
- 작업자가 멈추면 임대 시간이 지난 작업을 다시 가져올 수 있습니다.
- 일시적인 기반 시설 오류만 정해진 횟수만큼 재시도합니다.
- 이전 작업자가 늦게 보낸 결과는 최신 결과를 덮을 수 없어야 한다고 완료 조건에 적었습니다.

실제 서비스에 필요한 최소한의 복구 기준이 이미 들어 있습니다.

### 2.5 외부에서 들어오는 값을 신뢰하지 않는다는 원칙이 분명합니다

- 요청 본문 크기와 JSON 형식을 검사합니다.
- UUID와 날짜·시간 형식도 실제로 검사하도록 요구합니다.
- 인증 정보, 쿠키, 토큰, 개인정보와 운영 DB 원본을 받지 않습니다.
- `reproductionData`의 값을 명령이나 SQL로 실행하지 않습니다.
- 검증 명령은 서비스 설정에 미리 등록된 것만 사용합니다.

입력 형식뿐 아니라 저장, Codex 전달, 명령 실행까지 같은 원칙이 이어집니다.

### 2.6 완료 조건을 실제로 확인할 수 있게 작성했습니다

가짜 Codex를 사용한 전체 흐름 시험과 실제 SDK 연동 시험을 분리했습니다. 중복 접수, 작업자 중단, 임대 만료, 오래된 승인, 정책 위반도 시험하도록 적어 두었습니다. 정상 흐름만 확인하는 계획보다 훨씬 안전합니다.

## 3. 구현 전에 반드시 보완할 사항

### 확정됨: 승인 요청은 본문 없이 처리합니다

DEC-007은 다음과 같이 확정했습니다.

- 승인 API는 요청 본문을 받지 않습니다.
- 서버가 인시던트를 잠근 뒤 성공한 분석이 정확히 하나인지 확인합니다.
- 서버가 해당 분석 ID와 기준 커밋을 승인 및 패치 실행 기록에 복사합니다.
- 같은 `Idempotency-Key`를 다시 보내면 기존 승인 결과를 반환합니다.
- 다른 키로 이미 승인된 인시던트를 다시 승인하거나 승인 가능한 상태가 아니면 `409`를 반환합니다.

현재 MVP는 인시던트마다 분석을 한 번만 수행하고 재분석을 지원하지 않으므로 이 방식이 가장 단순합니다. 재분석을 추가할 때 분석 버전 또는 분석 ID를 승인 요청에 포함하는 방식을 다시 검토하면 됩니다.

### 확정됨: 작업 재실행과 최대 실행 시간을 제한합니다

DEC-011과 DEC-021은 다음과 같이 확정했습니다.

- 작업을 가져갈 때마다 임의의 UUID인 `claim_token`을 새로 만듭니다.
- 작업 유지 신호와 최종 결과 저장은 `job_id + claim_token + status=RUNNING`이 모두 맞을 때만 허용합니다.
- 작업을 다시 가져가면 이전 `claim_token`은 무효가 됩니다.
- 작업자는 30초마다 임대를 갱신하며, 120초 동안 갱신되지 않은 작업만 다시 가져갑니다.
- 임대 갱신에 실패하거나 소유권을 잃으면 진행 중인 Codex 실행을 취소하고 결과를 버립니다.
- 일시적인 기반 시설 오류만 최초 실행을 포함해 최대 3회 시도합니다. 다시 시도할 때는 새 토큰, 새 Codex 대화와 새 작업 공간을 사용합니다.
- 분석 한 번의 최대 실행 시간은 24시간입니다. 이 제한에 도달하면 다시 시도하지 않고 최종 실패로 처리합니다.
- 이전 토큰으로 보낸 유지 신호와 최종 결과가 DB 행을 하나도 바꾸지 못하는지 통합 시험으로 확인합니다.

작업자 동시 실행 수가 1이어도 이 보호 장치는 필요합니다.

### P0-1. 분석할 때 사용한 서비스 정책을 승인과 패치까지 고정해야 합니다

서비스 설정에는 저장소 위치, 실행 지침, 허용·금지 경로와 검증 명령이 들어 있습니다. 이 설정을 시작할 때 `services.policy`에 반영하는 흐름도 있습니다. 하지만 분석한 뒤 승인하거나 패치하기 전에 설정이 바뀌면 어느 값을 따라야 하는지는 정해져 있지 않습니다.

예를 들어 사용자가 분석 결과를 확인한 뒤 허용 경로나 검증 명령이 바뀌면, 사용자가 본 조건과 실제 패치에 적용되는 조건이 달라집니다. 승인보다 느슨해진 정책이 적용되면 안전 경계도 무너집니다.

최소한 다음 값을 분석 실행 기록에 고정해 두는 것이 좋습니다.

- 정책 버전 또는 정책 내용의 해시
- 허용 경로와 금지 경로
- 검증 명령
- 실행 지침 파일 목록
- 사용할 모델과 응답 형식 버전

패치는 현재 서비스 설정이 아니라 승인된 분석에 저장된 값을 사용해야 합니다. 더 단순하게 구현하려면 분석 뒤 서비스 설정이 바뀐 경우 승인을 `409`로 거부해도 됩니다.

### P0-2. Codex와 검증 명령의 외부 통신을 기본적으로 막아야 합니다

문서에서는 `Sandbox.read_only`와 `Sandbox.workspace_write`로 파일 접근 권한을 나눴고, 비밀 정보와 환경 변수도 전달하지 않도록 했습니다. 하지만 외부 네트워크 접근을 허용할지 여부는 적혀 있지 않습니다.

읽기 전용은 파일을 쓰지 못하게 하는 기능이지 외부 통신까지 막는다는 뜻은 아닙니다. 악의적인 저장소 문구나 오류 입력이 외부로 정보를 보내도록 유도할 수 있고, 검증 명령이 인터넷에서 임의 코드를 내려받을 수도 있습니다.

첫 MVP에서는 다음처럼 단순하게 막는 것이 안전합니다.

- 분석, 패치, 검증 명령은 모두 외부 네트워크 접근을 기본적으로 차단합니다.
- 패키지 설치, 원격 저장소 가져오기, 원격 측정 정보 전송을 허용하지 않습니다.
- 패치 작업 중에는 `fetch`, `pull`, `push`를 실행하지 않습니다.
- 꼭 필요한 사내 패키지 저장소가 생기면 나중에 별도 허용 목록을 정합니다.
- 프록시와 관련 환경 변수가 제거되고 외부 접속이 실패하는지 연동 시험으로 확인합니다.

## 4. 구현할 때 해석이 갈릴 수 있는 사항

### P1-1. 새 오류 발생과 인시던트 버전의 관계

인시던트에는 발생 횟수인 `occurrence_count`와 동시 변경을 막는 `version`이 있습니다. 작업 결과를 저장할 때는 작업자가 읽었던 `version`과 현재 값이 같아야 합니다. 하지만 분석 중 같은 원인의 오류가 새로 들어오면 발생 횟수와 `version`을 함께 올릴지 정해져 있지 않습니다.

둘을 함께 올리면 정상적으로 끝난 분석도 새 오류가 한 번 들어왔다는 이유로 결과를 저장하지 못할 수 있습니다.

첫 MVP에서는 `version`을 상태 변경과 승인 충돌을 막는 용도로만 쓰는 것이 단순합니다. 새 오류가 들어올 때는 `occurrence_count`와 `updated_at`만 바꾸고 `version`은 그대로 두는 편이 좋습니다.

### P1-2. 분석에 어느 시점까지의 오류를 넣을지 정해야 합니다

문서에서는 인시던트를 처음 만들 때 분석 작업을 한 번만 등록합니다. 그러나 작업자가 분석을 시작하기 전이나 분석하는 도중 같은 원인의 오류가 추가되면 이를 현재 분석에 넣을지 정해져 있지 않습니다.

첫 MVP에서는 다음처럼 정하면 충분합니다.

- 작업자가 분석을 가져간 시점까지 저장된 오류만 이번 분석에 사용합니다.
- 분석 중 새로 들어온 오류는 발생 횟수에는 반영하지만 현재 분석을 다시 시작하지는 않습니다.
- 분석 결과에 `inputOccurrenceCount`나 `inputCutoffAt`을 저장해 어느 시점의 입력인지 남깁니다.
- 다시 분석하는 기능은 MVP 이후로 미룹니다.

### 확정됨: 재시도할 때 실행 기록도 함께 갱신합니다

- 재시도할 수 있는 오류라면 작업과 실행 기록을 같은 트랜잭션에서 `PENDING`으로 바꾸고 오류와 시도 횟수를 남깁니다.
- 더는 재시도하지 않는다면 작업, 실행 기록, 인시던트를 같은 트랜잭션에서 실패 상태로 바꿉니다.
- 작업과 실행 기록의 ID는 유지하되, 이전 Codex 대화와 작업 공간은 버리고 새로 만듭니다.
- 24시간 분석 제한에 도달한 경우는 재시도할 수 없는 오류로 분류합니다.

### P1-4. 분석 결과와 저장 자료의 크기를 정해야 합니다

입력 요청은 256 KiB로 제한하고 패치 파일 수와 변경 줄 수도 제한합니다. 하지만 다음 결과물에는 아직 구체적인 상한이 없습니다.

- 분석 결과 전체 크기
- 근거와 변경 제안 항목 수
- Git 변경 내용 크기
- 검증 명령의 표준 출력과 오류 출력 크기
- 저장할 오류 설명과 API 응답 크기

설정을 지나치게 늘릴 필요는 없습니다. 분석 결과, Git 변경 내용, 명령 출력, 배열 항목 수의 네 가지 상한만 정해도 충분합니다. 저장하기 전에 비밀 정보를 가리고 크기를 줄이며, 같은 기준을 계약 시험으로 확인하면 됩니다.

### P1-5. 어디까지 공개할 서비스인지 정해야 합니다

현재 문서의 “인증 없이 개발망에만 공개”라는 기준은 내부 기술 검증용 MVP로는 일관됩니다. 다만 네트워크에서 접근할 수 있는 내부 제품으로 운영하려면 승인 API 보호가 본질적인 기능이 됩니다.

- 로컬 또는 폐쇄된 개발망에서만 쓴다면 실제로 해당 주소에만 연결되도록 강제합니다.
- 여러 사용자가 접근하는 내부 서비스라면 오류 발신 서비스용 토큰과 승인자용 토큰 정도는 추가합니다.

첫 MVP부터 OIDC나 역할 기반 권한 관리까지 넣을 필요는 없습니다.

### P1-6. JSON Schema의 엄격 검사 방식을 하나로 정해야 합니다

AJV의 JSON Schema 2020-12 검사에는 통과하지만, 여러 자료형을 `type: [...]`으로 적은 부분에서 엄격 검사 경고가 발생합니다.

여러 도구에서 같은 결과를 얻으려면 각 자료형을 `anyOf`로 풀어 쓰는 편이 좋습니다. `allowUnionTypes` 설정을 사용한다면 검사기 설정과 계약 시험에 그 선택을 분명히 남겨야 합니다.

## 5. 첫 MVP에 그대로 남겨야 할 기능

1. 설정 파일로 단일 서비스 등록
2. HTTP 오류 접수와 JSON Schema 검사
3. 중복 접수 방지와 같은 원인의 오류 묶기
4. PostgreSQL에 상태와 작업을 안전하게 저장
5. 저장소를 바꾸지 않는 Codex 분석
6. 분석 결과 조회
7. 분석 ID, 기준 커밋, 정책이 고정된 승인
8. 승인 후 별도 작업 공간과 새 Codex 대화에서 패치
9. 실제 Git 변경 내용에 대한 안전 정책 검사
10. 미리 등록한 검증 명령 실행
11. 변경 내용과 검증 결과 조회
12. 가짜 Codex 전체 흐름 시험과 실제 SDK 연동 시험

## 7. 문서별 검토 결과

### `docs/mvp-scope.md`

제품의 목표, 필수 기능, 제외할 기능과 안전 원칙이 잘 정리되어 있습니다. 남은 필수 보완 사항 두 가지를 추가하면 범위 문서로 충분합니다. 페이지 나누기와 실패한 작업 공간 보존은 필수 기능이 아니라 후속 운영 항목으로 내리는 것이 좋습니다.

### `docs/decision-register.md`

확정, 제안, 미결정을 나누고 중요도를 표시한 방식이 좋습니다. DEC-007, DEC-011, DEC-021은 이번 검토에서 확정했습니다. DEC-004/005/006/008/012/013은 구현 전에 한 번에 확정하는 편이 좋습니다.

아래 두 가지 결정도 추가할 것을 권합니다.

- 분석 당시 서비스 정책 고정
- Codex와 검증 명령의 외부 네트워크 차단

### `openapi/auto-error-handler-mvp.v1.yaml`

여섯 개 API만으로 필요한 흐름을 충분히 표현합니다. 승인 API는 요청 본문 없이 서버가 승인 대상을 고정하도록 계약이 정리됐습니다. 결과물 크기 제한과 인증을 사용하지 않는 이유를 `security: []`로 명시하면 구현자가 계약을 다르게 해석할 가능성이 줄어듭니다.

OpenAPI 문법 검사는 통과했습니다. 인증 설정, 태그 설명과 로컬 서버 주소에 관한 경고가 남아 있습니다.

### `schemas/external-error-event-v1.schema.json`

사람이 읽는 재현 설명과 실제 재현에 쓸 구조화 입력을 나눈 점이 좋습니다. 받을 수 있는 헤더를 제한하고 명령이나 SQL을 구조적으로 받지 않도록 한 방향도 적절합니다.

AJV의 JSON Schema 2020-12 검사는 통과했습니다. 여러 자료형을 적은 부분의 엄격 검사 경고와 UUID·날짜 형식 실패 사례만 보완하면 됩니다.

### `docs/implementation-contracts.md`

트랜잭션 범위, 고유 제약, 부분 인덱스, 작업 가져오기, Git과 Codex의 경계가 실제로 구현할 수 있을 만큼 구체적입니다.

`claim_token`, 30초 유지 신호, 120초 임대, 최대 3회 시도와 24시간 분석 제한은 반영됐습니다. 분석 당시 정책 고정과 새 오류와 상태 버전의 관계는 추가로 정해야 합니다.

### `docs/mvp-execution-plan.md`

구현 순서와 완료 조건이 잘 잡혀 있습니다. 가짜 구현으로 전체 흐름을 먼저 연결한 뒤 실제 Codex 연동으로 넓히는 순서도 적절합니다.

구현 전 단계에 남은 필수 보완 사항 두 가지를 넣고, 페이지 나누기와 별도 지표 수집, 실패한 작업 공간 보존을 후속 단계로 내리면 계획이 더 작고 분명해집니다.

## 8. 사용자가 결정할 항목

아래 항목만 확정하면 요구사항 검토를 마치고 구현으로 넘어가도 됩니다.

- [ ] 분석을 시작할 때 서비스 정책과 설정을 실행 기록에 고정
- [ ] Codex, 패치, 검증 명령의 외부 네트워크 접근을 기본 차단
- [ ] 인시던트 `version`은 상태 변경과 승인 충돌을 막는 용도로만 사용
- [ ] 첫 MVP에서 목록 커서와 실패한 작업 공간 보존 제외
- [ ] 로컬·폐쇄망 검증으로 한정할지, 간단한 토큰 인증까지 포함할지 결정

## 9. 최종 의견

큰 방향을 다시 설계할 필요는 없습니다. 제품이 해결할 문제, 사람이 승인해야 하는 지점, Git과 명령 실행의 안전장치, 실패 복구와 시험 기준이 전반적으로 잘 연결되어 있습니다.

지금 필요한 것은 요구사항을 더 늘리는 일이 아닙니다. 정책 고정과 외부 통신의 두 가지 계약을 확정하고, 새 오류의 세부 의미를 짧게 정리하면 됩니다. 페이지 나누기와 장기 운영 기능은 첫 MVP에서 덜어내도 됩니다.

이 작업까지 마치면 문서 정리는 충분하며 구현으로 넘어가도 됩니다.
