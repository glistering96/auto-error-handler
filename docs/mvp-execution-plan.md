# Auto Error Handler MVP 실행 계획

이 문서는 최초 PostgreSQL 중심 구현 계획의 기록입니다. 현재 실행 방법과 SQLite 기본값·PostgreSQL 확장 경계는 [README](../README.md), [ADR-0003](decisions/0003-sqlite-local-postgresql-scaleout-and-review.md), [후속 작업 계획](review-web-sqlite-scaleout-plan-2026-09-25.md)을 따릅니다.

상태: MVP 설계·계약 기준 확정 · Phase 1 구현 시작 가능
작성일: 2026-09-05
결정 반영: 2026-09-24
범위: MVP 수직 흐름만

이 문서는 기존 [세부 구현 계획](implementation-plan.md)에서 **MVP 구현 순서와 작업 단위만 분리한 실행 문서**입니다. 기존 문서는 세부 계약과 확장 준비를 참고하는 자료로 유지합니다.

## 1. 최종 목표

```text
Phase 0 문서·결정·계약 정리
  → Phase 1 기반 코드·DB·품질 검사
  → Phase 2 오류 접수·사건·작업
  → Phase 3 작업자·가짜 분석
  → Phase 4 읽기 전용 Codex 분석
  → Phase 5 승인·패치·변경 내역 검증
  → Phase 6 실패 주입·E2E·완료 체크리스트
```

완료 기준은 “Codex가 답을 냈다”가 아니라, 승인 전 무변경과 승인 후 제한된 검증 diff를 반복 가능한 테스트로 증명하는 것입니다.

## 2. Phase 0 — 구현 전 결정·계약 정리

아래 값은 [의사결정 대장](decision-register.md)에서 확정했습니다. 결정 자체는 완료됐으며, 설정·마이그레이션·계약 시험에 반영하는 구현 작업은 아직 남아 있습니다.

| 결정 | 확정한 MVP 값 | 구현할 때 함께 맞출 대상 |
|---|---|---|
| DEC-004 ID | 내부 ID는 UUIDv4 | 마이그레이션, 예제 데이터 |
| DEC-005 사건 묶기 | Producer 지문 필수, 같은 서비스·지문·전체 SHA만 묶음 | 이벤트 검증, 부분 고유 인덱스, 동시 접수 시험 |
| DEC-006 기준 저장소·SHA | 새 사건 접수 때 저장소 경로를 고정하고, 새 이벤트의 SHA 또는 당시 기본 브랜치 `HEAD`를 전체 커밋 SHA로 고정 | 접수 처리, Git 오류 응답, 설정 변경 시험 |
| DEC-007 승인 | 요청 본문 없이 서버가 유일하게 성공한 분석과 기준 SHA를 승인 트랜잭션에서 확정하고, `Idempotency-Key` 헤더는 필수로 받음 | OpenAPI, 승인 API 테스트 |
| DEC-008 제한 | 요청 256 KiB, 재현 데이터 깊이 8·값 1,000개, 변경 10파일/400줄, 패치 900초, 명령당 300초 | 설정, 서비스 구성, 경계값 시험 |
| DEC-011 작업 임대와 재시도 | 임대 120초, 생존 신호 30초, 선점할 때마다 UUID 토큰 발급, 일시적인 기반 시설 오류만 총 3회 시도 | 작업 마이그레이션, 작업자 테스트 |
| DEC-012 동시성 | 기본값 1, 미완료 작업 최대 100개 | 설정, 과부하 응답, 작업자 시험 |
| DEC-013 Codex 수명 주기 | 시도마다 `AsyncCodex` 컨텍스트와 새 스레드, 안정 버전 고정 후 종료 동작 검증 | Codex 어댑터 계약, 잠금 파일, 통합 시험 |
| DEC-021 분석 최대 실행 시간 | 분석 하나는 최대 24시간 실행하고 시간 초과는 재시도 없이 최종 실패 | 설정, Codex 어댑터, 시간 초과 테스트 |
| DEC-014 산출물 | 성공·실패 작업 트리를 실행 종료 때 삭제하고 DB 결과는 MVP 개발 기간 동안 보존 | 작업 공간 계약, 정리 시험 |
| DEC-015/016 API 조회 | 커서는 `(created_at, id)`를 외부에서 해석할 수 없게 인코딩함. 기본 20개·최대 100개를 반환하고, 생성 전 분석·패치 조회에는 `404`를 반환 | OpenAPI, API 테스트 |
| DEC-017 오류 코드 | 고정된 오류 코드 목록과 민감 정보를 제거한 상세 내용 사용 | 구현 계약, `Problem` 시험 |
| DEC-022/023 정책·통신 | 첫 분석 선점 때 정책 고정 사본 저장, 모델 연결은 허용하고 실행 명령의 외부 접속 차단 | DB, Codex·검증 실행 환경, 통합 시험 |
| DEC-024 분석 입력 | 사건의 첫 이벤트만 분석 입력으로 사용, 추가 발생은 `version`을 올리지 않음 | DB, 분석 조회, 동시 접수 시험 |
| DEC-025 이벤트 체크섬 | RFC 8785 정규화 JSON의 SHA-256, 중복 키·정규화 불가 수치 거부 | 접수 처리, 멱등성·경계값 시험 |

요청 데이터 체크섬은 [RFC 8785의 JSON 정규화 방식](https://www.rfc-editor.org/rfc/rfc8785.html)으로 만든 UTF-8 바이트의 SHA-256으로 계산합니다. 객체 키 순서나 공백만 다른 요청은 같은 데이터로 보고, 문자열 값과 배열 순서는 그대로 비교합니다. 중복 객체 키는 `400`, 정규화할 수 없는 JSON 수치는 `422`로 거부합니다. 7자리 이상으로 입력된 커밋은 저장소에서 확인한 전체 커밋 객체 ID(40자리 또는 64자리)로 바꾸어 저장하고, 모호하거나 커밋이 아닌 객체는 `422`로 거부합니다.

## 3. 모듈 의존 순서

```text
형식화된 설정 / 오류 코드 목록
        ↓
DB 마이그레이션 / 도메인 상태 전이
        ↓
접수 트랜잭션 ───────────→ 조회 API
        ↓
임대 기반 작업자 ─────────→ 가짜 분석
        ↓                         ↓
workspace manager ───────→ real Codex analysis
        ↓
승인 트랜잭션
        ↓
패치 실행기 → 변경 내역 검증기 → 검증 명령 실행기 → 패치 결과
        ↓
failure injection / E2E / 완료 체크리스트
```

API, 작업자, Codex, Git을 각각 따로 완성하지 않습니다. 각 단계에서 가짜 구현과 계약을 먼저 확정한 뒤 다음 단계로 이동합니다.

## 7. 구현자가 시작하면 안 되는 조건

- P0 결정이 `OPEN`인 채로 OpenAPI·migration·승인 handler를 확정하려는 경우
- 실제 Codex SDK를 가짜 게이트웨이보다 먼저 일반 CI에 넣으려는 경우
- 승인 계약 없이 쓰기 가능한 작업 트리를 만드는 경우
- 이벤트 요청 데이터의 문자열을 셸 명령, SQL, 테스트 명령으로 실행하려는 경우
- 설정된 argv allowlist 없이 임의 command를 실행하려는 경우
- 기준 SHA를 확인하지 않고 default branch 최신 상태를 사용하려는 경우
- diff를 저장하기 전에 path·binary·symlink·submodule 검사를 생략하는 경우

## 8. MVP 이후 전환 조건

MVP E2E가 통과한 뒤에만 다음을 별도 설계합니다.

1. GitHub App과 Draft PR
2. 서비스·승인자 인증과 감사용 식별 정보
3. 알림과 사용자 작업 흐름
4. Outbox/RabbitMQ/DLQ가 필요한 처리량·장애 요구 검증
5. sandbox, object storage, HA, 멀티테넌시

RabbitMQ를 먼저 넣는 것은 MVP의 증명 범위를 넓히므로, PostgreSQL polling이 실제 병목이라는 측정 결과가 있을 때 별도 ADR로 진행합니다.
