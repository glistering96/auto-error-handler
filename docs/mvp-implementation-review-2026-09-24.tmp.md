# MVP 구현 계획·서비스 구조 검토

상태: 과거 검토 기록 — 지적한 설계 공백의 결정 반영 완료
검토일: 2026-09-24
범위: 현재 작업 트리의 설계 문서와 API·이벤트 계약. 실행 코드의 동작 검증은 포함하지 않음.

> 2026-09-24 후속 결정: 이 문서는 결정을 내리기 전의 검토 기록으로 보존합니다. 아래 미결정 지적 중 기준 SHA, 지문·ID, 정책 고정 사본, 실행 환경 통신 경계, 분석 입력, 제한값은 [의사결정 대장](decision-register.md)과 [결정 기록](decisions/README.md)에 확정했고 관련 계약을 갱신했습니다. 구현·계약 시험은 아직 끝나지 않았습니다.

## 결론

MVP의 제품 목표와 구현 순서는 적절하다. 오류 접수 → 사건 묶기 → 읽기 전용 분석 → 사람 승인 → 격리된 패치 → 실제 변경 내역과 검증 결과 조회라는 핵심 흐름이 `docs/mvp-scope.md`와 `docs/mvp-execution-plan.md`에 연결되어 있다. 접수·승인 트랜잭션, 작업 임대와 `claim_token`, 허용 경로 및 검증 명령도 설계되어 있다.

다만 **계획이 곧바로 구현 가능한 최종 계약은 아니다.** 의사결정 대장에 P0 `OPEN`·`PROPOSED` 항목이 남아 있고, 기준 SHA의 확정 시점과 분석 당시 정책을 승인까지 유지하는 방식에 공백이 있다. 현재 작업 트리에는 실행 코드, 마이그레이션, 테스트가 없으므로 MVP 구현 완료나 실행 가능 여부를 판단할 단계도 아니다.

## 잘 잡힌 부분

| 항목 | 확인한 근거 | 평가 |

| 승인 경계 | `CORE-004`, `DEC-007`, `DEC-018`, 승인 트랜잭션 계약 | 승인 전 `PATCH` 작업과 쓰기 가능한 작업 트리를 만들지 않는 불변 조건이 분명함 |
| 장애 복구 | `DEC-011/021`, `jobs.claim_token`, 조건부 생존 신호·완료 처리 | 이전 작업자의 늦은 결과를 거부하도록 설계됨 |

## 구현 전 해결할 문제

### P0-1. 기준 SHA를 고정하는 시점이 문서마다 다르다

`DEC-006`과 `docs/mvp-execution-plan.md`는 `release.commitSha`가 없으면 **최초 접수 시점**의 기본 브랜치 `HEAD`를 고정하도록 권장한다. 반면 `docs/service-architecture.md`의 분석 순서는 작업자가 분석을 시작할 때 기준 SHA를 결정한다. 작업 대기 중 브랜치가 이동하면 처음 오류를 접수했을 때와 다른 코드를 분석할 수 있다.

권고: `DEC-006`을 확정하고, 사건을 처음 접수할 때 기준 SHA를 조회·검증한 뒤 사건 생성 트랜잭션에 고정해 저장할지 명시한다. 외부 Git 조회와 DB 트랜잭션의 경계, SHA 조회 실패 시 응답 및 재시도 의미, 기존 사건에 다른 SHA의 이벤트가 들어올 때의 처리까지 계약 테스트로 고정한다. 접수 시점 고정을 선택한다면 Phase 2에서 구현하고 Phase 4에는 작업 트리 생성과 SHA 재확인만 둔다.

근거: `docs/decision-register.md` DEC-006, `docs/mvp-execution-plan.md` Phase 0·2·4, `docs/service-architecture.md` 5.1·5.2.

### P0-2. 분석 당시 정책의 고정 사본이 DB 계약에 없다

`services.policy`는 저장하지만 `analysis_runs`에는 기준 SHA와 결과만 기록하도록 되어 있다. 분석과 승인 사이에 허용 경로, 실행 지침, 모델 또는 검증 명령이 바뀌면 승인자가 본 분석과 다른 조건으로 패치를 만들 수 있다. 앞선 임시 검토 문서도 이를 지적했으나 현재 의사결정 대장과 실행 계획에 결정·할 일이 반영되어 있지 않다.

권고: 분석 시작 시 `analysis_runs.policy_snapshot`에 실행 지침 경로, 허용·차단 경로, 변경량·시간 제한, 검증 명령 인자 배열, 모델, 구조화 결과 형식 버전을 저장한다. 승인과 패치는 승인된 분석 실행의 고정 사본을 사용하고 현재 `services.policy`를 다시 읽지 않는다. 정책 변경 전후의 승인·패치 통합 시험을 Phase 5에 추가한다. 이 내용은 아직 제안이며 기존 `ACCEPTED` 결정으로 표시하지 않는다.

근거: `docs/implementation-contracts.md`의 `services`·`analysis_runs`·승인·`PatchRequest`, `docs/mvp-implementation-review-2026-09-12.tmp.md`의 P0-1.

### P0-3. 실행 환경의 외부 통신 정책을 실제 연결 구조에 맞춰 정해야 한다

기존 검토 문서는 분석·패치·검증 명령의 외부 통신을 모두 차단하자고 제안한다. 그러나 `docs/service-architecture.md`의 실행 모델에는 Codex 앱 서버에서 OpenAI로 이어지는 연결이 있다. 모든 프로세스의 통신을 일괄 차단하면 실제 Codex 경로도 작동하지 않는다.

권고: Codex 서비스 호출에 필요한 통신과 Codex가 실행하는 도구·검증 명령의 통신을 분리해 정책을 작성한다. 검증 명령의 외부 접속은 기본 차단하고, Codex 실행 환경은 필요한 연결만 허용하는 방식을 실행 환경 통합 시험으로 확인한다. 샌드박스의 파일 쓰기 제한만으로 네트워크 차단이 성립한다고 간주하지 않는다. 정확한 허용 대상과 차단 방식은 실행 환경 확인 후 결정한다.

근거: `docs/service-architecture.md` 6절, `docs/mvp-implementation-review-2026-09-12.tmp.md` P0-2.

### P0-4. P0 미결정 항목을 Phase 0에서 닫아야 한다

`DEC-004`(ID), `DEC-005`(사건 지문), `DEC-006`(기준 SHA), `DEC-008`(크기·시간 제한), `DEC-012`(동시성), `DEC-013`(Codex 수명 주기)이 아직 `OPEN` 또는 `PROPOSED`다. 일부 권장값은 범위·실행 문서에서 사실상 확정값처럼 읽힌다. 최종 마이그레이션과 API 계약을 이 상태로 작성하면 구현자가 서로 다른 값을 택할 수 있다.

권고: `docs/decision-register.md`의 상태를 먼저 확정하고, OpenAPI·JSON Schema·DB 계약·설정·계약 시험을 같은 변경에서 맞춘다. 상세 계획에 쓰인 숫자는 그때까지 권장값으로만 취급한다.

근거: `docs/decision-register.md` 구현 의사결정 표, `docs/mvp-execution-plan.md` Phase 0.

### P1-1. 새 발생 기록이 들어올 때 분석 입력과 상태 버전의 의미가 불분명하다

분석 중 같은 지문의 이벤트가 추가될 수 있다. 현재 계약은 작업 완료 시 사건 `version` 일치를 요구하지만, 발생 횟수 증가가 `version`도 올리는지는 정하지 않았다. 동시에 어떤 시점까지의 발생 기록을 분석 입력에 포함했는지도 남기지 않는다. 정상 분석이 신규 발생 한 건 때문에 완료되지 못하거나, 결과가 어느 입력을 설명하는지 알기 어려워질 수 있다.

권고: `version`을 상태 전이용으로 쓸지 명시하고, 분석 선점 시 입력 기준 시각 또는 마지막 발생 기록 ID와 건수를 고정한다. 이후 들어온 이벤트의 처리를 계약 시험으로 정한다.

근거: `docs/implementation-contracts.md` `incidents.version`·완료 처리, `docs/mvp-implementation-review-2026-09-12.tmp.md` P1-1/2.

### P1-2. 같은 지문에 다른 배포 SHA가 들어오는 경우를 정해야 한다

현재 처리 중인 사건의 유일성은 `(service_id, fingerprint)`로 정의되어 있다. 따라서 같은 지문이지만 `release.commitSha`가 다른 이벤트도 하나의 사건에 묶일 수 있다. 사건은 기준 SHA 하나에서 분석하므로 새 발생의 코드와 분석 대상 코드가 다를 수 있다.

권고: 서로 다른 검증된 SHA를 같은 사건에 묶을지, 새 사건으로 분리할지 `DEC-005/006`에서 결정한다. 어느 쪽이든 발생 기록과 분석의 기준 SHA 관계를 조회 결과에 드러내고 동시 접수 시험을 추가한다.

근거: `docs/implementation-contracts.md`의 사건 부분 고유 인덱스·기준 SHA, `docs/contracts/external-error-event-v1.md`의 사건 묶기.

### P1-3. `reproductionData`의 깊이·값 크기 제한은 설명에만 있다

외부 계약은 최대 깊이와 항목 수를 적용한다고 말하지만, JSON Schema의 재귀적 `jsonValue`에는 최대 깊이 제한이 없고 문자열 길이 제한도 없다. 전체 요청 256 KiB 제한도 아직 `DEC-008`의 권장값이다. 스키마 검증 전에 요청 크기·중첩 깊이·항목 수를 어디서 검사할지 구현 계약으로 정해야 한다.

권고: 본문 크기를 JSON 파싱 전에 제한하고, 파싱 후 중첩 깊이와 총 항목 수를 검사한다. 이 제한을 일반 CI의 계약 시험에 추가한다. 스키마만으로 비식별화가 끝난다고 표시하지 않는다.

근거: `docs/contracts/external-error-event-v1.md` 4절, `schemas/external-error-event-v1.schema.json`의 `$defs.jsonValue`.

### P2. 문서 진입점의 끊어진 링크와 예시 ID를 정리해야 한다

현재 작업 트리에서 `README.md`가 가리키는 기존 HTML 두 파일은 삭제 상태이고 새 Walkthrough 링크도 아직 파일이 없다. HTTP 이벤트 계약의 `incidentId` 예시는 ULID 형식인 반면 DB 초안은 UUID를 가정한다. 새 HTML을 진입점에 연결하거나 기존 링크를 정리하고, `DEC-004` 확정 후 예시를 통일하면 된다.

근거: 현재 `git status`, `README.md` 문서 링크, `docs/contracts/external-error-event-v1.md` 응답 예시, `docs/implementation-contracts.md` 식별자 규칙.
