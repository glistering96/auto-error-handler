# Auto Error Handler MVP 구현 범위

상태: 구현 범위 확정 · 구현과 시험 대기
작성일: 2026-09-05
결정 반영: 2026-09-24
기준: [MVP 의사결정 대장](decision-register.md)

이 문서는 현재 설계에서 **MVP로 실제 구현할 요소만 추려 정리한 범위 문서**입니다. 세부 필드와 상태가 문서마다 다르면 `ACCEPTED` 결정, OpenAPI·JSON Schema, 마이그레이션, 계약 테스트 순서로 판단합니다.

현재 `HEAD`에는 설계 문서만 있으며 Python 패키지, FastAPI·작업자 진입점, PostgreSQL 마이그레이션, Docker Compose 구성, 테스트는 없습니다. 따라서 이 문서는 구현 완료 보고서가 아니라 구현 범위와 완료 조건을 정의합니다.

## 1. MVP 한 문장

등록된 예제 저장소에서 발생한 오류 이벤트를 접수하고 PostgreSQL로 사건과 작업을 관리합니다. 사람이 Codex의 읽기 전용 분석 결과를 승인한 경우에만 기준 SHA에서 분리한 작업 트리에 제한된 패치를 만들고, 검증을 마친 변경 내역을 제공하는 전체 흐름을 완성합니다.

## 2. 반드시 구현할 요소

| 영역 | MVP 구현 요소 | 관찰 가능한 결과 |
|---|---|---|
| 서비스 등록 | 설정 파일 기반 서비스, 저장소 경로, 기본 브랜치, 실행 지침, 허용·차단 경로, 검증 명령 인자 | 시작할 때 설정과 저장소를 검증하고 `services`에 등록함 |
| 오류 접수 | `POST /v1/error-events`, JSON Schema, 요청 본문 256 KiB 제한, `Idempotency-Key`와 `eventId` 일치 검사, 필수 `fingerprint`와 선택적 `reproductionData` 수신, 접수 시 전체 기준 SHA 확정 | 유효한 요청에는 `202`, 잘못된 요청에는 `Problem` 응답을 반환함. 요청 입력과 예제 데이터 초기값을 정규화해 분석에 전달함 |
| 멱등성 | `(service_id, event_id)` 고유 제약과 정규화한 요청 데이터의 체크섬 | 같은 요청 데이터를 다시 보내면 새 발생 기록이나 작업을 만들지 않고, 요청 데이터가 다르면 `409`를 반환함 |
| 사건 | Producer가 보낸 지문 정규화, `(service_id, fingerprint, base_commit_sha)`로 처리 중인 사건 묶기, 발생 기록 누적 | 같은 지문·기준 SHA의 이벤트만 하나의 사건으로 묶임 |
| 상태 저장 | `services`, `error_events`, `incidents`, `occurrences`, `analysis_runs`, `approvals`, `patch_runs`, `jobs` | API 프로세스 재시작 후에도 상태가 복구됨 |
| 비동기 실행 | PostgreSQL 작업 대기열, `SKIP LOCKED` 기반 작업 선점, 120초 임대, 30초 생존 신호, UUID `claim_token`, 최대 3회 시도 | 같은 작업이 중복 실행되지 않고 작업자 장애 후 복구됨 |
| 분석 | 사건의 첫 이벤트와 첫 선점 때 저장한 정책 고정 사본, 기준 SHA의 읽기 전용 작업 트리, 새 Codex 스레드, 최대 실행 시간 24시간, 구조화된 `AnalysisResult` 검증 | 원인·근거·변경 제안·검증 계획을 저장하고, 분석 중에는 저장소에 변경 내역이 생기지 않음 |
| 결과 조회 | 사건 목록·상세, 분석, 패치 조회 | 실행 중·성공·실패 상태와 결과를 API로 확인할 수 있음 |
| 승인 | 요청 본문 없이 서버가 유일하게 성공한 분석·기준 SHA·정책 고정 사본을 확정하고 승인·패치 실행·`PATCH` 작업을 원자적으로 저장 | 승인 전에는 쓰기 가능한 작업 트리와 `PATCH` 작업이 없음 |
| 패치 | 승인된 SHA의 새 쓰기 가능 작업 트리, 분석에 사용한 것과 다른 새 Codex 스레드 | 승인된 분석·SHA와 연결된 패치 실행 기록이 생성됨 |
| 안전 검증 | 허용·차단 경로, 파일 수·변경 줄 수 제한, 바이너리·심볼릭 링크·하위 모듈 차단, `git diff --check` | 정책을 위반하면 검증 명령을 실행하기 전에 `PATCH_FAILED`로 전환됨 |
| 테스트 실행 | 서비스 설정에 등록된 인자 배열만 `shell=False`로 실행, 시간·출력 제한 | 모든 검증을 통과한 경우에만 `PATCH_READY`로 전환됨 |
| 산출물 | 변경 내역, 변경 파일, 검증 결과, 민감 정보를 제거한 오류를 DB에 저장하고 성공·실패 작업 트리를 실행 종료 때 정리 | API에서 검증 가능한 변경 내역과 결과를 조회할 수 있음 |
| 로컬 실행 | PostgreSQL Compose 구성, 상태·준비 상태 점검, 가짜 Codex 게이트웨이, 결함이 있는 예제 저장소 | 실제 Codex를 호출하지 않고도 일반 CI와 종단 간 테스트를 재현할 수 있음 |

## 3. MVP 상태와 불변 조건

### 사건 상태

```text
RECEIVED
  → ANALYZING
  → AWAITING_APPROVAL
  → PATCHING
  → VALIDATING
  → PATCH_READY

RECEIVED/ANALYZING → ANALYSIS_FAILED
PATCHING/VALIDATING → PATCH_FAILED
```

MVP에서는 거절, 승인 만료, 재분석, 재패치, 자동 병합, 원격 브랜치 전송을 구현하지 않습니다.

### 반드시 지켜야 하는 불변 조건

1. PostgreSQL을 사건·실행·작업 상태의 단일 기준 정보로 사용합니다.
2. 오류를 접수할 때 이벤트, 사건·발생 기록, `ANALYZE` 작업을 하나의 트랜잭션으로 저장합니다.
3. 승인할 때 승인, 패치 실행, `PATCH` 작업, 사건 상태를 하나의 트랜잭션으로 저장합니다.
4. Codex·Git·검증 작업은 DB 트랜잭션 밖에서 실행합니다.
5. 승인 트랜잭션이 끝나기 전에는 `PATCH` 작업과 쓰기 가능한 작업 트리를 만들지 않습니다.
6. 분석은 읽기 전용 샌드박스와 작업 트리만 사용합니다. 패치는 승인된 SHA에서 만든 새 작업 트리와 새 스레드만 사용합니다.
7. Codex 응답을 최종 증거로 사용하지 않고 실제 Git diff와 실행 결과를 다시 검사합니다.
8. 스키마 오류, 정책 위반, 존재하지 않는 커밋, 테스트 실패는 자동으로 재시도하지 않습니다.
9. 이벤트 요청 데이터, `reproductionData`, 스택 추적, 명령 출력은 용량을 제한하고 민감 정보와 초과 내용을 제거한 뒤 저장합니다. 로그에는 원문을 남기지 않습니다.
10. 새 사건의 저장소 경로는 접수 때 고정하고, 새 이벤트의 기준 SHA는 전체 커밋 ID로 확정합니다. 분석 작업자는 둘을 다시 선택하지 않습니다.
11. 사건의 첫 이벤트만 분석 입력으로 사용하고, 이후 발생 기록은 건수와 시각만 갱신합니다. 추가 발생은 상태 전이용 `version`을 올리지 않습니다.
12. 승인·패치·검증은 분석 때 저장한 `analysis_runs.policy_snapshot`을 사용하며 현재 서비스 정책을 다시 읽지 않습니다.
13. 모델 연결은 허용하되 Codex가 실행하는 명령과 검증 명령의 외부 접속은 차단합니다. 이를 강제하지 못하면 실제 모델 경로는 준비 완료로 표시하지 않습니다.

## 4. MVP에서 제외할 요소

다음은 MVP 수직 흐름을 완성한 뒤 별도 단계로 둡니다.

- 서비스 인증, 승인자 인증, OIDC/RBAC
- 외부 또는 내부 RabbitMQ, Outbox, DLQ, replay 도구
- 멀티테넌시와 조직별 격리
- 웹 콘솔, Slack/Teams/Discord 알림
- GitHub App, branch push, Draft PR, 자동 merge
- 자동 배포, Kubernetes, 운영용 HA
- Secret Manager, 객체 스토리지, 중앙 장기 로그
- 사용자가 직접 재분석·재패치·거절하는 작업 흐름

단, MVP에서도 이후 교체할 수 있도록 `IngressAdapter`, `CodexGateway`, `WorkspaceManager`, `ValidationRunner` 경계는 둡니다. 후속 기능 자체를 미리 구현하지는 않습니다.

## 5. 기존 문서에 추가해야 하는 MVP 요소

현재 문서의 핵심 흐름에는 포함되어 있으나 구현자가 빠뜨리기 쉬운 항목을 MVP 필수 조건으로 승격합니다.

### 5.1 실행 전 준비 상태

- 서비스 설정의 저장소 경로가 허용된 최상위 경로 아래에 있고 실제 Git 저장소인지 확인합니다.
- 기본 브랜치와 기준 커밋이 존재하는지 확인합니다.
- `release.commitSha`가 있으면 해당 SHA를 사용하고, 존재하지 않으면 조용히 다른 SHA로 바꾸지 않고 실패시킵니다.
- `release.commitSha`가 없을 때만 새 이벤트를 접수하는 시점의 기본 브랜치 `HEAD`를 전체 커밋 ID로 고정합니다. 기존 `eventId`의 재전송은 Git을 다시 조회하지 않습니다.
- 검증 명령이 인자 배열이며 허용 목록에 등록되어 있는지 시작할 때 확인합니다.
- 준비 상태 점검에서 Codex 모델과 실행 환경, 작업 공간 최상위 경로, 데이터베이스 연결 설정을 확인합니다.

### 5.2 실패·중복·취소 의미

- API는 `traceId`를 생성해 반환하고 작업·실행·오류 코드를 연결합니다.
- 분석·패치의 시간 초과, 통신 실패, 구조화된 출력 검증 실패, 정책 위반, 검증 실패를 서로 다른 오류 코드로 저장합니다.
- 만료된 임대를 회수한 뒤 늦게 도착한 이전 작업자의 결과는 `claim_token` 불일치로 저장하지 못하게 합니다.
- heartbeat가 정상인 동안에는 lease를 계속 연장하며, 분석이 24시간에 도달하면 재시도 없이 최종 실패로 처리합니다.
- 중복 승인에서 같은 idempotency key뿐 아니라 같은 Incident에 이미 승인된 경우의 응답/`409` 의미를 고정합니다.
- 정상 종료를 시작하면 새 작업 선점을 중지하고 실행 중인 작업을 취소합니다. 취소한 작업은 임대 만료 후 복구할 수 있어야 합니다.

### 5.3 데이터·산출물 보호

- 요청 데이터, 분석 결과, 변경 내역, 표준 출력·표준 오류 각각에 저장 용량과 반환 용량의 상한을 둡니다.
- 비밀값 형태와 인증 헤더·쿠키가 저장되지 않는지 확인하는 민감 정보 제거 테스트를 둡니다.
- 성공·실패 작업 트리는 실행이 끝날 때 삭제합니다. 결과와 길이를 제한한 진단 내용은 MVP 개발 기간 동안 DB에 보존합니다.
- API 응답에 내부 절대 경로, credential, 원본 secret, 전체 stack trace를 노출하지 않습니다.

### 5.4 운영 최소선

- `/health/live`와 `/health/ready`를 분리합니다.
- 구조화 로그에 `traceId`, `jobId`, `incidentId`, `runId`, `workerId`를 넣되 요청 데이터 원문은 넣지 않습니다.
- 대기열 길이와 대기 시간, 작업 선점, 실행 시간, 재시도, 실패, 정리 실패를 최소한 로그나 지표로 남깁니다.
- 작업자 동시성 1과 대기 작업 수 상한을 기본값으로 두어 로컬 디스크와 Codex 실행을 보호합니다.

### 5.5 공식 문서 검토 후 추가한 필수 할 일

- 처리 중인 동일 지문 사건에는 부분 고유 인덱스를 적용합니다. 동시 요청에서 고유 제약 위반이 발생하면 기존 사건을 다시 조회합니다.
- 작업을 선점할 때 `(available_at, created_at, id)` 순서로 정렬합니다. `SKIP LOCKED`로 인해 오래된 작업이 계속 밀리는 현상과 만료된 임대를 검사합니다.
- `base_commit_sha`에는 저장소가 실제로 반환한 전체 객체 ID를 저장할 수 있어야 합니다. 짧은 SHA가 여러 객체를 가리키면 실패로 처리합니다.
- 요청 본문 용량을 초과한 경우 OpenAPI·외부 계약·오류 코드 목록에서 모두 `413 Content Too Large`와 같은 고정 오류 코드를 사용합니다.
- 계약 테스트에서 JSON Schema의 UUID·날짜-시간 `format`을 실제 검증 조건으로 적용합니다.
- 외부 오류 요청 데이터와 저장소 내용은 신뢰할 수 없는 데이터로 취급합니다. 프롬프트 삽입 공격, 비밀 파일, 프로세스 환경 변수의 격리 경계를 테스트합니다.
- 실제 재현 입력인 `reproductionData`에는 요청 입력, 예제 데이터 초기값, 기능 플래그만 허용합니다. 명령·SQL·인증 정보·운영 DB 덤프는 거부합니다.
- Git·작업 트리 명령에도 고정된 인자 배열, 최상위 경로 검증, 저장소 단위 잠금을 적용합니다.

이 항목들이 기존 문서의 큰 기능 목록에는 빠져 있었지만, 동시성·보안·계약 관점에서 MVP가 실제로 안전하게 동작하기 위한 필수 구현 요소입니다.

## 6. MVP 완료 체크리스트

아래를 모두 만족해야 MVP 완료로 봅니다.

- 예제 서비스 등록부터 오류 접수·분석·승인·패치·검증·변경 내역 조회까지 전체 흐름이 한 번 실행됩니다.
- 같은 `eventId`를 세 번 보내도 이벤트·발생 기록·분석을 중복 생성하지 않습니다.
- 서비스·지문·전체 SHA가 같고 이벤트가 다른 요청은 하나의 처리 중인 사건에 누적됩니다. SHA가 다르면 별도 사건을 만듭니다.
- 사건의 첫 이벤트와 분석 정책 고정 사본이 재시도·승인·패치에서도 바뀌지 않습니다.
- 분석 전후에 기준 저장소 작업 트리의 변경 내역이 비어 있습니다.
- 성공한 분석 실행이 정확히 하나가 아니거나 승인 가능한 상태가 아니면 `409`를 반환합니다.
- 승인 전에는 `PATCH` 작업과 쓰기 가능한 작업 트리가 없습니다.
- 허용 경로 밖의 변경, 바이너리·심볼릭 링크·하위 모듈 변경, 변경량 제한 초과가 발생하면 `PATCH_FAILED`로 전환하고 검증 명령을 실행하지 않습니다.
- 검증에 실패한 작업은 `PATCH_READY`가 될 수 없습니다.
- 작업자 비정상 종료, 만료된 임대, 시간 초과, 작업 공간 정리, 중복 승인을 다루는 테스트가 통과합니다.
- 이전 `claim_token`으로 보낸 생존 신호와 결과는 저장되지 않습니다. 정상적인 생존 신호가 이어지는 장기 분석은 중복 실행되지 않습니다.
- 가짜 Codex를 사용하는 일반 CI 경로와 실제 SDK를 검증하는 별도 통합 테스트 경로가 분리되어 있습니다.

## 8. 필수 구현 구성 검토 결과

| 검토 항목 | 현재 상태 | 판단 |
|---|---|---|
| 오류 접수·멱등성·사건 묶기 | 문서와 Phase 2 할 일에 포함됨 | 구현 가능. 동시 요청을 위한 부분 고유 인덱스 보완 필요 |
| PostgreSQL 작업 대기열·임대·재시도 | 문서와 Phase 3 할 일에 포함됨 | 구현 가능. 동일 시각의 정렬 기준과 오래된 작업이 밀리는 현상에 대한 검사 추가 |
| 읽기 전용 분석·승인·쓰기 가능한 패치 | 문서와 Phase 4~5 할 일에 포함됨 | 핵심 흐름 구성됨. SDK 시간 초과와 정리 동작은 통합 테스트 필요 |
| 변경 정책·검증 명령 | 문서와 Phase 5 할 일에 포함됨 | 구현 가능. Git 명령과 검증 명령 모두 인자 배열 경계 필요 |
| HTTP 승인 계약 | 요청 본문 없이 서버가 성공 분석과 기준 SHA를 고정 | DEC-007과 OpenAPI에 확정됨 |
| 내부 ID·재시도·작업자 동시성 | 의사결정 대장에서 값 확정 | 마이그레이션·처리기·계약 시험 구현 대기 |
| 실행·보안·관측 | 준비 상태, 민감 정보 제거, 프롬프트 삽입 공격, 상태 점검, 정리 작업 추가 | MVP 필수 항목으로 구성됨 |
| 실제 구현물 | Python 패키지, 마이그레이션, Compose 구성, 테스트 부재 | 아직 구현 단계가 아니라 문서 단계 |

핵심 기능과 주요 설계 결정은 실행 계획에 반영했습니다. Phase 0의 문서 기준은 확정됐으며 Phase 1 구현을 시작할 수 있습니다. 설정·마이그레이션·자동화 계약 시험은 해당 구현 단계의 완료 조건입니다.
