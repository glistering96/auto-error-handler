오류에서 검증된 변경 내역까지

현재 저장소의 설계 문서를 바탕으로 만든 MVP 구조도입니다. 다이어그램의 요소를 누르면 역할, 관련 계약, 실제 문서 조각을 확인할 수 있습니다.

설계 문서 단계외부 입력: HTTP상태·작업: PostgreSQL산출물: 검증된 Git 변경 내역
한눈에 보기

오류 이벤트를 사건으로 묶고 PostgreSQL 작업자가 읽기 전용 분석을 수행합니다. 사용자가 분석을 승인하면 새 작업 트리에서 패치를 만들고 실제 Git 변경 내역과 등록된 검증 명령을 확인한 뒤 결과를 저장합니다. 이 흐름은 설계된 목표이며 아직 실행 코드로 구현되지 않았습니다.

전체 흐름

보라색은 서비스가 소유하는 처리, 회색은 외부 주체와 실행 환경, 밝은 보라색은 PostgreSQL 상태입니다. 확대·이동하거나 요소를 눌러 상세 계약을 볼 수 있습니다.

반드시 지켜야 할 경계

MVP의 핵심은 분석 결과를 안전하게 검증된 변경 내역으로 연결하는 데 있습니다.

01 · 접수

사건과 작업을 함께 저장

이벤트, 사건·발생 기록, 최초 분석 작업을 하나의 트랜잭션으로 저장합니다. 같은 eventId는 중복 작업을 만들지 않습니다.

02 · 분석

저장소는 읽기 전용

기준 SHA의 분리된 작업 트리에서 분석합니다. 분석 중에는 쓰기 가능한 패치 작업 트리와 PATCH 작업이 존재하지 않아야 합니다.

03 · 승인

사람이 확인한 분석에 묶음

승인 요청은 본문 없이 받습니다. 서버가 성공한 분석과 SHA를 잠금 트랜잭션에서 확인한 뒤 승인·패치 실행·작업을 함께 저장합니다.

04 · 실행 소유권

늦게 도착한 결과 거부

작업을 선점할 때마다 새 claim_token을 발급합니다. 생존 신호와 완료 처리는 현재 토큰을 가진 작업자만 수행합니다.

05 · 패치

실제 변경 내역 확인

새 작업 트리의 Git 변경 내역으로 경로, 파일 종류, 변경량을 확인합니다. 정책 위반이면 검증 명령을 실행하지 않습니다.

06 · 검증

등록된 명령만 실행

서비스 설정에 등록된 인자 배열을 셸 없이 실행합니다. 모든 검증이 통과해야 PATCH_READY가 됩니다.

상태와 데이터

API와 작업자는 별도 프로세스이지만 아래 기록을 PostgreSQL에서 공유하도록 설계되어 있습니다.

RECEIVED → ANALYZING → AWAITING_APPROVAL → PATCHING → VALIDATING → PATCH_READY
분석 실패: ANALYSIS_FAILED · 패치/검증 실패: PATCH_FAILED

상태 전이는 설계 계약입니다. 실제 DB 마이그레이션과 상태 전이 코드는 아직 없습니다.

기록역할중요한 연결
services저장소와 실행 정책하나의 서비스에 여러 이벤트·사건
error_events수신 이벤트와 멱등성 검사(service_id, event_id) 고유
incidents / occurrences같은 지문·전체 SHA의 사건과 개별 발생 기록첫 이벤트를 분석 입력으로 고정
analysis_runs분석 상태·결과·기준 SHA·정책 고정 사본승인은 성공한 분석 하나를 가리킴
approvals / patch_runs승인한 분석·SHA와 패치·검증 결과사건당 승인·패치 실행 하나
jobs분석·패치 비동기 작업과 임대현재 claim_token으로 완료를 제한

접수 시 코드를 고정

새 사건에는 접수 당시 저장소 경로를, 새 이벤트에는 배포 SHA 또는 현재 기본 브랜치 HEAD의 전체 커밋 ID를 고정합니다. 중복 이벤트는 Git을 다시 조회하지 않습니다.

첫 이벤트만 분석

내부 ID는 UUIDv4, 지문은 필수입니다. 같은 서비스·지문·전체 SHA만 묶고, 추가 발생은 분석 입력이나 상태 version을 바꾸지 않습니다.
